## 第一轮面试讲解

1. **为何 engine 已构建成功还崩溃？** engine 是网络执行计划；context 是一次执行的
   状态和 tensor 地址。局部 context 已创建，但旧代码在成员指针赋值前调用它，
   属于初始化顺序问题。GDB 确认崩溃在 loader，原始输出和修复后同输入结果一起保留。
2. **为何不能只填 mBindings？** executeV2 接收地址数组；enqueueV3 依赖 context
   上按 tensor 名注册的地址。只保留旧数组不完成新接口的绑定契约。
3. **为何 batch 维度会影响后处理？** scores 的原始布局是 [1,3000,9]；旧 SSD
   消费端按非 batch 的 [3000,9] 解释候选框数和类别数。尺寸转换错了，即使没有崩溃，
   也可能产生错误解析；所以同时验证形状、实际 GPU 执行和有限值。
4. **enqueueV3 返回就能复用输入吗？** 不能；它表示提交成功，GPU 可能仍在读取。
   本轮探针显式等待 stream 完成，未来执行层用 event 保护在途 slot。
5. **1,800 帧无 sequence 缺口能证明不丢帧吗？** 只能说明这个驱动序号观测窗口。
   应用队列主动丢弃、结果帧龄和用户态等待需要其他计数与同一时钟域的时间点。
6. **1,712 次推理是不是性能结论？** 不是正式 benchmark。窗口含模型初始化、JPEG
   和日志开销，也未做 warmup 排除、三次重复及固定功耗/热状态。

尚未验证的内容直接说明阶段和下一项验收，不用“应该支持”替代实测结果。
